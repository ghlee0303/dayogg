# 엔지니어링 의사결정 기록

이 문서는 넉넉한 인프라가 아니라 **주어진 환경 안에서 원하는 결과를 최대한 끌어내려 한 과정**을 담는다. 특히 초당 10회로 묶인 외부 API가 이 서비스의 처리량을 규정하는데, 이 제약을 그대로 둔 채 문제마다 새 미들웨어를 붙이기 전에 이미 가진 수단(가상 스레드, 스택에 이미 있는 컴포넌트, 프레임워크 기본 기능)으로 풀리는지 먼저 확인했다. 후보를 나란히 비교해 왜 그 선택이 이 제약에 맞는지 근거를 남겼다.

- 스택: Java 21 (Virtual Threads) · Spring Boot 4.0 · MySQL · Redis · 단일 EC2 인스턴스 배포
- 도메인: 배틀로얄 게임 "이터널리턴"의 플레이어 전투 통계 수집·집계·제공 백엔드

---

## 1. 전적 수집 파이프라인 개선 (동기 블로킹 → 비동기 SSE 잡 + 멱등 합류)

### 배경 및 문제정의

- **상황**: 플레이어 전적을 수집하려면 외부 게임 API(**초당 10회, 10 RPS 제한**)를 `next` 커서로 페이징하며 호출해야 함. **요청을 받는 시점에 몇 번 호출할지 알 수 없음** (신규 유저 1회 ~ 시즌 내내 플레이한 유저 수백 회)
- **문제**: 동기 방식은 요청 스레드가 수 초~수십 초 동안 HTTP 커넥션을 물고 있어 타임아웃에 노출되는데, 그 대기 시간의 대부분은 CPU 연산이 아니라 외부 API I/O(레이트리밋 대기 포함)에 있음

---

### 1-1. 대기 스레드 낭비 — 가상 스레드 (플랫폼 스레드 대신)

#### 솔루션: 태스크마다 가상 스레드

- **분석**: 수집 잡은 CPU 연산이 거의 없고 네트워크 I/O + 레이트리밋 대기가 전부인 **I/O bound** 작업. 동시에 수십 개 잡이 대부분 "멈춰서 기다리는" 상태로 공존해야 함
- **전략**: 태스크마다 가상 스레드를 새로 만들어 잡을 실행하고, 잡 로직은 동기 블로킹 코드 그대로 둠. 동시 실행 수는 세마포어로 제한해 외부 API·DB를 보호하고, 퍼밋을 못 얻은 요청은 429로 거절. 잡 전체가 아니라 DB 반영 구간만 짧은 트랜잭션으로 감싸 긴 API 대기 동안 커넥션을 물지 않게 함

#### 기술 선정: 가상 스레드 vs 플랫폼 스레드 풀

**가상 스레드 채택**

| | 플랫폼 스레드 풀 | 가상 스레드 |
|---|---|---|
| 대기 중 비용 | OS 스레드 1개 점유 (스택 ~1MB 상주) | 블로킹 시 캐리어 스레드 반납, 힙에 재개 지점만 |
| 동시 대기 한계 | 풀 크기 = 동시 잡 수 상한 | 수천 개까지 소수 OS 스레드로 감당 |
| 처리량 늘리는 법 | 풀 확대 → 컨텍스트 스위칭·메모리 비용 | 스레드 증설 불필요 |
| 코드 스타일 | 동기 | 동기 그대로 (리액티브 재작성 불필요) |

- **플랫폼 스레드로 안 간 이유**: 이 워크로드에는 CPU 병렬성이 필요 없다. 필요한 건 "대량의 블로킹 대기를 값싸게 유지"하는 것이고, 플랫폼 스레드 풀을 그 수준으로 키우면 I/O 대기에 OS 스레드를 낭비하는 안티패턴이 된다. 

---

### 1-2. 결과·진행 전달 채널 — SSE (폴링·웹소켓 대신)

#### 솔루션: 서버→클라 단방향 스트림

- **분석**: 컨트롤러가 즉시 반환한 뒤, 수 초~수십 초 뒤의 완료/오류를 클라이언트로 밀어줄 채널이 필요. 흐름은 **서버→클라 단방향**, 클라→서버 스트림은 없음
- **전략**: 컨트롤러는 수집을 잡으로 넘기고 스트림 핸들만 즉시 반환. 잡이 끝나면 그 스트림으로 완료·오류 이벤트를 push하고, 같은 대상에 합류한 요청들의 스트림을 한 잡에 매달아 한 번에 브로드캐스트

#### 기술 선정: SSE vs 폴링 vs 웹소켓

**SSE 채택**

| | 폴링 | 웹소켓 | SSE |
|---|---|---|---|
| 방향 | 클라 주도 반복 요청 | 양방향 | 서버→클라 단방향 |
| 서버 부하 | 진행 중 내내 재요청 + 잡 상태 저장 필요 | 상시 연결·핸드셰이크·별도 프로토콜 | HTTP 연결 1개 유지 |
| 구현 비용 | 상태 조회 API + 클라 타이머 + 완료 감지 | 프레임워크·프록시/LB 설정·하트비트 | 컨트롤러 반환값을 `SseEmitter` 로 |
| 재연결 | 수동 | 수동/라이브러리 | 브라우저 `EventSource` 자동 |
| 적합성 | 폴 간격 튜닝·완료 지연 부담 | 양방향 불필요 = 과한 복잡도 | 단방향 알림에 정확히 맞음 |

- **SSE를 고른 이유**: `text/event-stream` 표준, 브라우저 `EventSource` 가 재연결까지 처리, Spring `SseEmitter` 로 컨트롤러만 바꾸면 됨. HTTP/1.1의 도메인당 커넥션 6개 제한·프록시 버퍼링이 트레이드오프지만 단일·단기 스트림이라 무해
- **웹소켓**: 클라→서버로 보낼 스트림이 없어, 양방향 채널은 별도 프로토콜·프록시/LB 설정·하트비트 관리를 얹을 뿐 이 요구에는 안 쓰임
- **폴링**: 잡 상태를 어딘가 저장하고 클라가 주기적으로 물어야 함. 요청 수가 늘고, 완료 감지가 폴 간격만큼 지연되며, 진행률을 실시간으로 못 줌

---

### 1-3. 중복 실행 제거 — 멱등 합류

#### 솔루션: 진행 중인 잡에 후속 요청을 합류

- **분석**: 같은 대상에 대한 동시 요청은 "새 작업"이 아니라 "같은 결과를 기다리는 구독자". 조회와 생성이 원자적이지 않으면 동시 요청이 각자 잡을 만든다(TOCTOU) → 먼저 등록된 `sseKey` 유실
- **전략**: 대상별 멱등 키로 진행 중인 잡을 표시. 후속 요청은 새로 실행하지 않고 그 잡의 `sseKeyList` 에 합류시켜, N개 요청이 잡 1개를 공유하고 완료 시 전원 같은 결과를 받음. "진행 중 확인 → 없으면 생성"은 **한 락 구간의 단일 메서드**(`joinOrCreate`)로 원자화(상세는 아래 저장 흐름)

| 항목 | 요청마다 독립 실행 (기존) | 멱등 합류 (전환) |
|---|---|---|
| 중복 수집 | 요청 수만큼 페이징 루프 반복 | 잡 1회만 실행 |
| 10 RPS 토큰 | 중복 소모 | 1회분만 소모 |
| 결과 정합성 | 여러 잡이 같은 행을 경합 저장 | 단일 잡이 저장, 경합 없음 |
| SSE 전달 | 나중 요청이 앞 요청의 `sseKey` 를 덮어씀 | `sseKeyList` 에 append, 전원에게 브로드캐스트 |

**저장 흐름** — 대상별 멱등 키로 Redis에 객체 하나를 두고, 그 안에 잡의 `jobId` 와 합류한 요청들의 `sseKeyList` 를 담는다. 첫 요청이 이 객체를 만들고, 뒤이은 요청은 같은 객체에 자기 `sseKey` 만 덧붙인다. 읽고-고치고-쓰는 구간 전체가 대상 키 단위 분산 락 안에서 일어나 경합이 없다. 잡이 끝나면 `sseKeyList` 전원에게 결과를 보내고 그 자리(같은 락 구간)에서 객체를 지운다.

```
Redis  key: idempotent:player-refresh:123   (TTL = sse.timeout-minutes, 5분)
       val: { jobId, sseKeyList }

r1  joinOrCreate → GET 없음 → { jobId=J9, sseKeyList=[r1] } 저장 → J9 반환 (잡 생성)
r2  joinOrCreate → GET 있음 → sseKeyList=[r1, r2] 로 갱신     → J9 반환 (합류, 잡 안 만듦)
finish → sseKeyList 전원에 결과 전송 → key 삭제
```

> 이 합류 구조는 두 갈래로 이어진다 — 멱등 상태·락을 어디에 둘지(아래 1-4), 그리고 로그 추적축을 요청/잡으로 나누는 문제(2번 항목 설계 3).

---

### 1-4. Redis를 고른 이유 — 멱등 상태 저장 · 분산 락

멱등 합류는 두 가지를 저장소에 요구한다: **대상별 진행 상태**와 **그 상태를 원자적으로 갱신할 락**. 둘 다 후보가 여럿이었지만 같은 결론(Redis)에 도달했고, 한 인프라로 묶여 운영 포인트가 늘지 않는다.

#### ① 멱등 상태 저장

- **요구**: 대상별 "진행 중" 플래그 + `sseKeyList`. *짧은 수명*(잡 시간), *잦은 조회*, *TTL 안전망 필수*(잡이 죽어도 다음 요청이 영원히 막히면 안 됨)
- **로컬(JVM) 캐시**: TTL 만료와 조회+생성 원자화를 직접 구현해야 함
- **RDB 테이블**: 트랜잭션·커넥션·정리 배치가 붙고, 잡 상태를 영속 데이터로 남길 이유가 없어 과함
- **Redis 채택**: `SET EX` 한 줄로 TTL(=`sse.timeout-minutes` 5분), O(1) 조회, 키 단위 원자 연산. 요구에 정확히 맞고 이미 캐시 용도로 스택에 있음

#### ② 조회+생성 원자화 (분산 락)

- **요구**: `joinOrCreate` 의 "진행 중 확인 → 없으면 생성"이 한 임계 구역이어야 함. 깨지면 동시 요청이 각자 잡을 만들고 먼저 등록된 `sseKey` 가 유실됨(TOCTOU)
- **DB 비관적 락**(`SELECT … FOR UPDATE`): 락을 잡는 내내 커넥션을 점유하는데, 이 경로엔 애초에 트랜잭션이 없음(1-1 참고)
- **별도 코디네이터**(ZooKeeper 등): 이 규모에 새 인프라를 들이는 비용이 큼
- **Redisson `@DistributedLock` 채택**: 멱등 상태를 이미 Redis에 두므로 락도 같은 저장소. 어노테이션으로 대상 키 단위 락을 걸고, 락 리스 타임아웃으로 홀더가 죽어도 데드락이 없음

> 두 관심사가 모두 Redis로 수렴 → **멱등 키와 그 키를 지키는 락이 같은 시스템 안**에 있어 정합성 추론이 단순하고, 운영은 Redis 하나만 본다.

## 2. 운영 로그 관측성 개선 (평문 → 구조화 JSON)

### 배경 및 문제정의

- **상황**: 단일 EC2 인스턴스에 컨테이너로 배포. 운영 로그 창구는 CloudWatch 하나이고, **CloudWatch는 수집량이 곧 요금**임
- **문제**: 평문 로그는 값이 message 문자열에 박혀 지연 시간·URI 같은 조건으로 질의·집계할 수 없음. 스택트레이스 직접 출력·표준 출력이 로깅 시스템을 우회해 "1줄 = 1이벤트" 전제를 깨고, 프레임워크 기본 로그가 그대로 흘러 수집량을 키움. SSE는 요청 스레드와 잡 스레드가 달라 단일 스레드명으로는 추적이 끊김

### 솔루션: 구조화 로깅 설계

#### 설계 1 — 로그 이벤트를 문자열이 아니라 구조화된 객체로

값을 로그 문장에 끼워 넣으면 message 문자열에 박혀서 지연 시간으로 거르거나 URI별로 집계하는 질의를 할 수 없다. 대신 값마다 이름을 붙여 **필드**로 싣고 이벤트를 JSON 객체 한 줄로 내보내면, 각 값이 타입까지 살아 있는(숫자는 number) 질의 대상이 된다. "1줄 = 1이벤트(객체)"는 로그 집계 도구들의 대전제이기도 하다.

```java
// 문장에 끼워 넣음 — message 안에 박혀 질의 불가
log.info("playerId: {}, {}ms", id, ms);

// 필드로 분리 — 각 값이 질의·집계 대상
log.atInfo()
   .addKeyValue("playerId", id)
   .addKeyValue("elapsedMs", ms)
   .log("refresh done");
```

```json
{"message":"refresh done","playerId":42,"elapsedMs":123}
```

#### 설계 2 — 값 주입 통로를 역할별로 3개로 분리

이벤트에 필드를 실으려면 "어디서, 어떤 수명으로 값을 넣느냐"를 먼저 정해야 한다. 요청 전체를 따라다녀야 하는 값(추적 id), 여러 계층에 흩어져 누적되는 값(호출 횟수·소요 시간), AOP가 닿지 않는 곳에서 즉석으로 남길 값은 성격이 전부 다르다. 하나의 API로 뭉뚱그리면 어딘가에서 타입이 뭉개지거나 값이 새므로, 통로를 셋으로 나눠 각자의 제약에 맞췄다.

| 통로 | 역할 | 발행 시점 | 값 타입 |
|---|---|---|---|
| **MDC** | 요청·잡 전체를 잇는 추적 축 | 같은 스레드의 모든 이벤트에 자동 부착 | String |
| **LogContext** | 여러 메서드에 걸쳐 도메인 값 누적 | 최외곽 `@ServiceLogging` 종료 시 한 번에 | Object |
| **StructuredLog** | 그 자리에서 이벤트 하나 발행 | `.log()` 즉시 | Object |

- **왜 하나로 못 합치나**: 세 통로의 제약이 서로 달라 역할이 갈린다.
  - **MDC** — String 전용이고 스레드의 모든 이벤트에 자동으로 붙는다. 그래서 개별 값이 아니라 *요청·잡 전체를 잇는 추적 축*(요청 id 등)에만 쓴다.
  - **LogContext** — ThreadLocal 에 값을 쌓았다가 최외곽 프레임에서 한 번에 비운다. 여러 계층을 거치며 누적되는 *도메인 값*(호출 횟수·경과 시간 등)에 맞다.
  - **StructuredLog** — AOP 가 감싸지 않는 지점(`SseService`·`ApiService` 등)에서 *그 자리에서 이벤트 하나를 즉석 발행*하는 용도다.

```java
// MDC — 진입 시 1회, 이 스레드의 모든 로그 줄에 붙는다
MDC.put("jobId", jobId);

// LogContext — 계층을 넘나들며 누적, 최외곽 @ServiceLogging 이 끝날 때 flush
LogContext.put("playerId", playerId);
LogContext.addLong("apiMillis", elapsed);   // API 호출마다 합산
LogContext.addLong("apiCount", 1L);

// StructuredLog — AOP 밖(SseService)에서 그 자리에서 한 줄
StructuredLog.info(log, "sse")
    .addKeyValue("sseKey", sseKey)
    .log("[SSE-SEND] sent");
```

```json
// 최외곽이 flush한 서비스 로그 한 줄 — MDC(jobId) + LogContext(playerId·apiMillis·apiCount)가 합쳐짐
{"message":"[refresh] done","jobId":"X9Y8Z7","layer":"service",
 "playerId":123,"apiMillis":1720,"apiCount":3,"elapsedMs":2015}
```

#### 설계 3 — 추적축을 `code`(요청)와 `jobId`(잡)로 분리

로그를 필드로 만든 다음 필요한 건 "한 요청에서 나온 줄들을 어떻게 다시 이어 붙이나"다. 보통은 요청마다 발급하는 id 하나면 충분하지만, 이 서비스는 컨트롤러가 즉시 반환하고 실제 일은 별도 잡 스레드에서 돌며, 같은 대상 요청 여러 개가 잡 하나에 합류한다(1번 항목의 SSE 잡 구조). 이때 특정 요청의 id를 잡 로그에 붙이면 합류한 나머지 요청은 자기 id로 잡 로그를 찾지 못한다. 그래서 **요청 단위 축과 잡 실행 단위 축을 따로 세우고**, 컨트롤러 로그에 둘 다 찍어 요청에서 잡 로그로 따라갈 수 있게 했다.

| 축 | 범위 | 부여 지점 |
|---|---|---|
| `code` | 요청 하나 | `ControllerLoggingAspect` (진입 시 `TraceCode.generate()`) |
| `jobId` | 잡 실행 1회 | `SseJobDispatcher` (신규 잡 생성 시 발급) |
| `idempotentKey` | 잡의 대상 (그룹핑용) | `SseJobDispatcher` |

```json
// 컨트롤러 로그 — 두 축이 함께 찍힌다
{"layer":"controller","code":"A1B2C3","jobId":"X9Y8Z7","http":{"uri":"/player/sse/refresh"}}

// 잡 로그 — jobId 로 이어짐 (code 는 없음)
{"layer":"service","jobId":"X9Y8Z7","playerId":123,"elapsedMs":2015}
```

- **왜 `idempotentKey` 로 잡을 특정하면 안 되나**: 키가 대상(플레이어)마다 고정된 값이라, 잡이 끝나면 삭제됐다가 다음 요청 때 같은 값으로 재생성된다. 이걸로 필터하면 서로 다른 실행이 섞인다. 실행 단위는 `jobId` 뿐이다.

### 기술 선정: 구조화 로깅 구현 (내장 구조화 로깅 vs logstash-logback-encoder)

**Spring Boot 내장 구조화 로깅 채택**

- **logstash-logback-encoder**: 기능은 풍부하나 외부 의존성이 추가되고 logback XML 설정이 늘어 운영 복잡도가 증가
- **내장 구조화 로깅**: Spring Boot 3.4+ 표준 기능이라 외부 의존성이 없음. `application.yml` 몇 줄로 JSON 출력을 켜고, SLF4J `LoggingEventBuilder`(`addKeyValue`)를 그대로 써서 필드를 붙인다.

운영 관측도 같은 기준으로 선택했다 — **Loki 상주 대신 CloudWatch를 질의 시점 pull**. 적재가 없어 안 보면 비용이 0이고, 로컬 Grafana에 read-only IAM 자격으로 CloudWatch 데이터소스만 연결해 로컬·운영 로그를 한 화면에서 본다.
